# テストのガイドライン

配置: `.claude/skills/testing-guideline/SKILL.md`

---

## 1. テストの種類と置き場所

| 種類 | 内容 | テストコード | 仕様書 | 実行方法 |
|---|---|---|---|---|
| サーバー側のテスト | リクエストを送り、応答・保存内容・表示される文言を確認する | `dokoutsu/tests/test_*.py`(画面ごと) | `docs/test/(画面コード)_(画面名).md` | `python3 manage.py test dokoutsu` |
| E2Eテスト | 実際のブラウザ(Playwright + Chromium)で画面を操作し、複数画面をまたぐ流れを確認する | `dokoutsu/e2e/e2e_*.py`(フローごと) | `docs/test/e2e_flows.md` | `python3 manage.py test dokoutsu.e2e -p "e2e_*.py"` |

- 「テスト」と言われたら、サーバー側のテストだけでなく、画面を操作するE2Eテストまで含めて考える
- テスト仕様書を作ってからテストコードを書く。仕様書の各ケースに、対応するテストメソッドと結果を記録する

## 2. スクリーンショット

- E2Eテストでは、主要な画面の状態ごとにスクリーンショットを取り、`docs/test/screenshots/(フローNo)_(状態).png`に保存する
- E2Eテストを実行したら、最新のスクリーンショットをコミットする
- E2E仕様書の各フローに、取得するスクリーンショットの一覧を書く
- 画面の見た目を変えない整理(リファクタリング)の前後では、スクリーンショットを比較し、見た目が変わっていないことを確認する
- 画面を作った・変えたときは、スクリーンショットとデザイン参考PDFの対応箇所を見比べる

## 3. 確認する観点

| 観点 | 内容 |
|---|---|
| エラーの表示 | 「保存されないこと」だけでなく、設計書のエラーメッセージが画面に表示されることまで確認する。E2Eでもブラウザ上に表示されることを確認する |
| 文字数 | 上限ちょうど(受け付ける)と上限+1文字(受け付けない)の両方を確認する |
| 文字の種類 | 半角英数字の項目には、日本語・全角数字・記号を入れて確認する |
| 形式 | 盤面データ・着手などの形式が決まっている値は、範囲外・不正な文字列・重複など、画面からは送られない値も送って確認する |
| 境界の時刻 | 有効期限・締切・送信回数の期間などは、境界の直前と直後の両方を確認する。時刻は`mock.patch`で固定し、実行するたびに結果が変わらないようにする |
| 画面の操作 | ボタンの活性条件(押せる・押せない)、選び直し、開き直したときの表示など、利用者の操作の流れを確認する |

## 4. 仕様書・設計書との対応

- 機能を追加・変更したら、影響する全ての画面のテスト仕様書にケースを追記する。1画面だけ書いて他の画面を漏らさない
- 詳細設計書の「4.1 UI要素の動作」の活性条件・「5. エラーケース」の各行に、対応するテストケースがあるかを確認する
- テストしていない項目があれば、仕様書と報告の両方で明示する

## 5. テストが失敗したとき

- テストを通すためにテストの内容を緩めない(CLAUDE.md「禁止事項」)
- 失敗は、実装の不具合かテストの誤りかを切り分けて報告する
- テストの誤り(確認のしかたの誤り)を直す場合も、確認する内容は緩めず、何をどう直したかを報告する

## 6. テストコードの書き方

- 各テストメソッドの先頭に、対応する仕様書のケース番号と、何を確認するかを1行で書く(例: `"""E3: 未確認アカウントではログインできない"""`)
- テストクラスには、対象の画面と仕様書の場所を書く
- 読んだだけでは意図が分かりにくい準備には、理由をコメントで書く(時刻の固定、セッションの直接操作、別のブラウザ(`self.client_class()`)を使う理由、IPアドレスの指定など)
- 複数のテストで使う補助関数は`dokoutsu/tests/helpers.py`、E2Eの共通の準備は`dokoutsu/e2e/base.py`に置く
