# コーディング規約

配置: `.claude/skills/coding-guideline/SKILL.md`

---

## 1. 基本方針

- Djangoの標準的な構成に従う
- 業務ロジックがviews.pyに集中したらservices.pyへ切り出す
- 1ファイル200行を超えたら分割を検討する
- 盤面コンポーネントの仕様は基本設計書「4.1 盤面」を参照
- HTMLはセマンティックな要素を使う(divの濫用を避け、header/nav/main/article/section/footer等、意味の通る要素を優先する)。独立したHTML規約は設けず、この1行を基準とする

## 2. 関連ガイドライン

- セキュリティ対策は `.claude/skills/security-guideline/SKILL.md` に従う

## 3. 冗長なコードを避ける

- 1箇所でしか使わない処理は関数に切り出さない
- 例外処理は実際に起こりうるケースのみ書く
- 既存の類似処理を確認してから書く

## 4. コメントの書き方

- 適用範囲: Python(views.py, models.py, services.pyなど)、JavaScript、CSS すべて
- 「読んで分からないところがない」レベルを基準にする(実装者の主観で「複雑かどうか」を判断しない)
  - 対象読者は自分自身(実装者=保守者)。基準は
    `.claude/skills/explain-for-skill-level/SKILL.md` に記録されたスキルレベルに従う
  - 同スキルで「要説明」と判定した概念を含むコードは、必ずコメントで意図・理由・
    仕組みを補う。判定の詳細・最新状態は同スキルを都度参照する
    (このファイルに個別項目を列挙して二重管理しない)
  - 「既知」と判定した概念は自明なものとして扱い、過剰なコメントを付けない
  - 例: 座標変換のロジック、非同期処理の順序保証
  - 例(CSS): flexbox/gridの入れ子で挙動が直感的でない箇所、z-index・positionの重なり調整、ベンダープレフィックスやハック的な指定の理由
- 「何をしているか」の説明だけでなく「なぜその実装・値・方針にしたか」を書く
- 単純な処理(単純なCRUD、getter/setter相当、標準的なセレクタ指定など)には過剰なコメントを付けない
