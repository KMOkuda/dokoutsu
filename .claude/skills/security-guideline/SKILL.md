# セキュリティ方針

> 配置: `.claude/skills/security-guideline/SKILL.md`
> 全画面・全機能に共通して適用する。

---

## 1. 本プロジェクトのリスク特性

| 項目 | 状況 |
|---|---|
| 公開範囲 | URLを知っていれば誰でも閲覧可能 |
| 認証 | 投稿・一覧はログイン必須、閲覧・回答投稿は不要 |
| 回答投稿の投稿者 | ログイン不要。ニックネームは必須だが、認証されない仮名 |
| 扱うデータ | 囲碁の局面、回答投稿。機微な個人情報は扱わない |

**特に注意すべき点**

- ログインなしで回答投稿できるため、スパム・荒らしへの耐性が必要
- ニックネームは認証されないため、他人と同じ名前を名乗れる(なりすまし)
- URLが漏れると第三者が閲覧できる前提で設計する
- 機微情報は扱わないが、アカウント情報(メールアドレス等)は保護対象

## 2. 必ず守る対策

### 2.1 Djangoの標準機能を無効化しない

| 機能 | 内容 |
|---|---|
| CSRF保護 | `{% csrf_token %}` を全フォームに入れる。`@csrf_exempt` を使わない |
| XSS対策 | テンプレートの自動エスケープを無効化しない。`|safe` や `mark_safe` を使わない |
| SQLインジェクション対策 | ORMを使う。`raw()` や文字列連結でのSQL生成をしない |
| クリックジャッキング対策 | `XFrameOptionsMiddleware` を有効のままにする |
| セッションCookieの保護 | `SESSION_COOKIE_HTTPONLY` を `True` のままにする(デフォルト値)。無効化するとJavaScript経由でセッションIDを読み取られる可能性がある。回答済み判定(F-05)がセッションに依存するため、特に重要 |

### 2.2 セッションの保持期間

- `SESSION_COOKIE_AGE = 60 * 60 * 24 * 120`(120日、約4ヶ月)に設定する
  (デフォルトは2週間だが、回答済み判定(F-05)の実用性を優先し、意図的に延長する)
- `SESSION_EXPIRE_AT_BROWSER_CLOSE` は `False`(デフォルト)のままとし、
  ブラウザを閉じても保持されるようにする
- セッションデータは `django_session` テーブルに蓄積される。期限切れデータを
  放置すると増え続けるため、定期的に `clearsessions` コマンドで削除する
  (運用開始後、実施方法・頻度は別途検討する)

### 2.3 認証・認可

- ログインが必要な画面には `@login_required` を付ける
- 「ログインしているか」だけでなく「その人が操作してよい対象か」を必ず確認する
  - 例: 問題の編集・削除は作成者本人のみ
- 権限チェックをテンプレート側の表示制御だけで済ませない。サーバー側で必ず検証する

### 2.4 入力値の検証

- Djangoのフォーム(`forms.py`)で検証する。ビューで手書きしない
- クライアント側(JavaScript)の検証は補助であり、サーバー側の検証を省略しない
- 文字数上限を必ず設定する(コメント本文、ニックネームなど)
- 盤面データは形式を検証する(想定外の構造を受け付けない)

### 2.5 URLの推測防止

- 問題のURLに連番のIDを使わない(UUID等を使用)
- 連番だと他人の問題を総当たりで閲覧できてしまうため

### 2.6 URL漏洩時の拡散防止

UUIDは推測は防げるが、漏洩後の転送・検索エンジンへのインデックス化までは防げない。
ログイン不要でUUIDのみを根拠に閲覧可能な画面(回答投稿画面・回答一覧画面)に、
以下を実装する。

| 対策 | 内容 |
|---|---|
| 検索エンジンへの非掲載 | 回答投稿画面・回答一覧画面のテンプレートに`<meta name="robots" content="noindex, nofollow">`を設定する |
| リファラー制御 | `settings.py`で`SECURE_REFERRER_POLICY = "same-origin"`を設定する。コメント内の外部リンクを開いても、UUID込みのURLがリファラーとして外部サイトに渡らないようにする |

### 2.7 秘密情報の管理

- `SECRET_KEY`、DBのパスワード、APIキーをソースコードに書かない
- 環境変数から読み込む
- `.env` ファイルを `.gitignore` に入れる
- 本番環境では `DEBUG = False` にする

## 3. ログインなし投稿への対策

| リスク | 対策 |
|---|---|
| スパム投稿 | 投稿頻度の制限を検討(同一IPから短時間に大量投稿を防ぐ) |
| なりすまし | ニックネームは認証されない旨を入力欄に明示する。ログイン済みの投稿を区別する表示を検討 |

> 第1イテレーションでは最低限の対策に留め、実際に問題が起きてから強化する。

---

## 4. 実装時のチェック項目

コードレビュー時に以下を確認する。

- [ ] フォームに `{% csrf_token %}` があるか
- [ ] `|safe` や `mark_safe` を使っていないか
- [ ] 権限チェックがサーバー側にあるか
- [ ] 入力値の上限が設定されているか
- [ ] 秘密情報がハードコードされていないか
- [ ] エラーメッセージに内部情報(ファイルパス、SQL等)が漏れていないか
- [ ] `SESSION_COOKIE_HTTPONLY` を `False` に変更していないか
- [ ] 回答投稿画面・回答一覧画面にnoindexが設定されているか
- [ ] `SECURE_REFERRER_POLICY` が設定されているか

---

## 5. 対象外とするもの

以下は本プロジェクトの規模・性質から、当面は対応しない。

| 項目 | 理由 |
|---|---|
| 二要素認証 | 仲間内利用のため過剰 |
| 監査ログ | 機微情報を扱わないため |
| 通信の暗号化(独自実装) | HTTPSをホスティング側で担保する |
