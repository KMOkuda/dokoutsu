# 基本設計書 作成ルール

## 1. 粒度: 基本設計には「システムとしてどう構成するか」だけを書く

基本設計書に書くのは、画面の存在・遷移・技術構成・共通コンポーネントの
仕様など、システム全体の骨格に関わることのみ。

1画面の中の操作手順・入力項目の詳細・エラーケース・処理の流れといった
「1画面を作るのに必要な情報」は詳細設計書(docs/design/(画面名).md)に書く。
基本設計書には持ち込まない。

判定基準: その記述が複数画面・システム全体に関わるか、それとも
1つの画面の実装者だけが必要とする情報か。後者なら詳細設計書へ。

移すべき内容の例:
- タップ回数、スナップ処理などの具体的な操作方式
- 入力項目ごとの検証ルール、初期値、最大長
- 画面内のUI要素の配置・動作
- エラーメッセージの文言
- その画面固有のデータ加工ロジック

## 2. 補足・括弧書きを付けない

要件定義書と同様、本文・表のセルに括弧での補足を詰め込まない。
条件や例外は別の表・別の章に出す。

## 3. 文体を統一する

- 表のセル内は句点(。)を付けない
- 常体で統一する
- 一文一意。文は長くしない

## 4. 章立ての基本構成

1. システム構成(構成図、技術スタック、採用しなかった構成)
2. 画面設計
   2.1 画面一覧(画面名・URL・概要・ログイン要否・対応要件・詳細設計へのリンク)
   2.2 要件の実現方式(要件定義書のF-XXごとに、実現方式を一文で対応させる表)
   2.3 画面遷移図(Mermaid)
3. 共通コンポーネント(複数画面で使う部品のみ。個別画面の部品は詳細設計へ)
4. 認証方式(認証基盤の選定のみ。要否は要件定義書を参照する形にし、重複させない)
5. ディレクトリ構成
6. 外部連携(あれば)

必要に応じて増減してよいが、増減した場合は章番号を振り直し、
本文中の相互参照も合わせて修正する。

## 5. 「2.2 要件の実現方式」の書き方

- 要件定義書のF-XXと1対1、または1対多で対応させる
- 1セルにつき1〜2文程度に留める。手順を書き始めたら詳細設計書へ移す合図
- 「〜する」で終わる短い文で、実現の方針だけを示す。手順・条件分岐は書かない

NG(詳細すぎる、詳細設計に属する):
「盤面をタップして石を配置する。1タップで確定し、最近傍の交点にスナップする。
黒石・白石を切り替えて配置でき、配置した石は取り消せる」

OK(基本設計の粒度):
「盤面をタップして石を配置し、局面として保存する」

## 6. 画面一覧の書き方

- 画面名、URL(末尾スラッシュなし)、概要(一文)、ログイン要否、対応要件ID、
  詳細設計書へのパスを表にする
- 概要は「何をする画面か」のみ。操作方法や表示項目は書かない
- 専用画面を持たない機能(一覧内で完結する操作、ログアウトのような
  リダイレクトのみの処理)は、画面名を「-」とし、URLと概要だけ記載する

## 7. 共通コンポーネントの書き方

- 複数画面で使う部品(盤面など)のみ記載する
- 「用途」「配置」「実装方針」「提供する機能」「満たすべき要求」を書く
- 具体的な操作方式(タップ回数、UIの詳細)は書かず、
  「各画面の詳細設計で定める」と明記して詳細設計側に委ねる

## 8. 修正時の必須チェック

基本設計書を修正するたびに、以下を確認する。

- [ ] 章番号・節番号が連番になっているか
- [ ] 本文中の他章・他ドキュメントへの参照が実際と一致しているか
- [ ] 削除した画面・要件への参照が残っていないか
- [ ] 詳細設計書に属する記述(操作手順、入力項目の細部)が紛れ込んでいないか
- [ ] 要件定義書と重複している記述がないか(特に認証要否、権限)
- [ ] 画面遷移図が画面一覧・実現方式の内容と矛盾していないか
- [ ] 文末の句点、文体(常体)が統一されているか

## 9. 要件定義書・テーブル定義書・詳細設計書との役割分担

| 内容 | 記載場所 |
|---|---|
| 利用者から見て何ができるか | 要件定義書 |
| 認証・権限の要否 | 要件定義書(基本設計書からは参照のみ) |
| システム構成、画面一覧、遷移、要件の実現方針 | 基本設計書 |
| テーブル・カラムの型/制約/初期値 | テーブル定義書 |
| 1画面の操作手順・入力項目・エラーケース・画面レイアウト | 詳細設計書(docs/design/) |

迷ったら「複数画面にまたがるか」で判断する。またがらないなら詳細設計書へ。

## 10. 出力形式

- Markdownで作成する
- 表を積極的に使う
- 構成図・ER図・画面遷移図はMermaid記法を使う
- 画面レイアウトの見た目はMermaidで表現しない(詳細設計書側でUI要素の動作・レイアウトの制約として書く)
