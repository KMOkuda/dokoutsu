# スキルレベルに応じた説明ルール

## 前提

ユーザーは「基本的にAIに書かせて、中身を理解できればいい」という方針。
コードを書くこと自体は代行してよいが、**何が起きているか説明を省略しない**。

## 判定方針

- **核となる使い方・考え方が分かれば「既知」とする。** 周辺の派生・レアケースまで
  すべて確認できていることを既知の条件にしない
- 「既知」は「完璧に理解している」ではなく「説明を省略してよい」という
  実務的な意味で使う
- 確認していない周辺知識は、リストに載せず放置する。実際にコードに出てきた
  タイミングで、その場で一言説明すれば足りる(先回りしてすべてを洗い出さない)
- 明確な誤解が確認された場合のみ、個別に記録して訂正対象とする

## 現在のスキルレベル

### HTML

- 基本タグは既知
- data属性・aria属性は未経験。使うときに説明する

### CSS

- 既知: Flexbox、疑似クラス・疑似要素(`:hover`、`::after`)、CSS変数、
  基本的なセレクタの組み合わせ(子結合子`>`、子孫結合子の半角スペース)
- 要説明: Grid全般
- 個別の誤解: 隣接兄弟結合子(`+`)を「1要素に複数クラス」と誤答した記録あり。
  実際に`+`を使うときは、直後の兄弟要素を指すという点を訂正して説明する

### JavaScript

- 既知: 基本文法、DOM操作の基本(`querySelector`/`querySelectorAll`、
  `addEventListener`、アロー関数)、非同期処理の概念(処理を一旦脇に置いて
  他の処理を進める、という仕組みレベルの理解)
- 要説明: 非同期処理の具体的な実装が複雑になる場面(複数の非同期処理を
  組み合わせる`Promise.all`等)、イベントのバブリングのような発展的な挙動

### Python

- 既知: 基本文法、内包表記(リスト・辞書とも同じ考え方として扱う)

### Django

- 既知: MTVの概念、デコレータという仕組み自体の存在
- 要説明: ORM(QuerySet、`filter`/`annotate`/`select_related`等)、
  フォームクラス、認証・認可の実装、ミドルウェア、シグナル。
  個別のデコレータ(`@login_required`以外)も初出時に一言添える

## コードを書く・提示する際のルール

### 1. 説明の要否

上記「要説明」に該当する概念を使うコードでは、コード提示の前後で説明する。
それ以外は既知として扱い、説明を省略してよい。

### 2. 説明の粒度

- 専門用語をそのまま使わず、身近な比喩か動作の言葉で説明する
- 「なぜそう書くか」より先に「これは何をしているか」を説明する
- 既知の概念との対比を積極的に使う
  (例: 「Gridは行と列を同時に指定できる点がFlexboxと違う」)
- 誤解が記録されている項目は、指摘してから正確な理解に修正する

### 3. 説明の置き場所

- コード内のコメントとしてではなく、**コードを提示する前後の会話文で説明する**
  (コーディング規約は「読んで分からないところがないレベル」でのコメントを求めているが、
  概念そのものの解説は会話文側の役割とし、コードコメントは実装の意図・理由に留める)
- 同じ概念を繰り返し使う場合、2回目以降は簡潔な言及のみでよい

## このドキュメントの更新

- 実装が進む中で自然に触れて理解が定着した概念は、都度「既知」に更新してよい。
  更新のたびに厳密な再テストは求めない。会話の中で本人が理解を示せば十分とする
- 新しい技術要素が出てきた場合、このリストにない概念として原則説明する
