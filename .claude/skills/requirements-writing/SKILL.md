# 要件定義書 作成ルール

## 1. 粒度: 要件定義には「何ができるか」だけを書く

要件定義書に書くのは、利用者から見て意味が通る要求のみ。
「どう実現するか」は基本設計書に書く。要件定義書には持ち込まない。

判定基準: その記述をユーザーに説明して意味が通るか。
通らない場合(技術用語、UI操作の詳細、URL、画面構成、DB構造など)は基本設計書へ。

移すべき内容の例:
- 操作方式(タップ回数、スナップ処理、ボタン配置)
- 画面名・URL・画面遷移
- データの保持形式、テーブル・フィールド名
- 入力欄の初期値、並び順などの表示の細部

NG(実現方法が混ざっている):
「盤面上に石を配置して問題を作成できる。19路盤で、1タップで確定し、
最近傍の交点にスナップする」

OK(要件のみ):
「出題したい局面を自分で作成する」
→ 盤面サイズ・タップ方式は基本設計書「3. 要件の実現方式」へ

NG(初期値の指定という実現方法が混ざっている):
「回答投稿はニックネームで行う。ログイン済みなら前回の名前を初期値とする」

OK(要件のみ):
「回答の意図や検討内容を文章で投稿する」
→ 初期値の挙動は基本設計書へ

## 2. 補足・括弧書きを付けない

要件は言い切りの一文で書く。「(〜の場合)」「(ただし〜)」のような括弧での
条件・例外・補足は原則付けない。

補足が必要な情報がある場合は、要件を分けるか、別の章(認証、非機能要件等)
に表として出す。1つの要件文に情報を詰め込まない。

NG: 「同じ問題に対する他の人の回答投稿を閲覧する(自分が回答済みであることが前提。ただし出題者は例外)」
OK: 「同じ問題に対する他の人の回答投稿を閲覧する」
   → 詳細な条件は5章「認証」や別途の表に出す

## 3. 文体を統一する

- 表のセル内は句点(。)を付けない
- 1文の中で文が続く場合(接続する場合)のみ句点を使ってよいが、それでも1文は短く保つ
- 一文一意を徹底する。1つのセルに複数の情報を詰め込まない
- 敬体(です・ます)ではなく常体(である体を省略した体言止め・動詞終止)で統一する

## 4. 権限・可視性などの横断項目は独立した章にする

個々の要件に条件を書き込まず、「認証」「非機能要件」のような横断的な章を
立てて、そこに一覧表としてまとめる。要件本文は短く保つ。

## 5. 章立ての基本構成

1. プロジェクト概要
2. 背景・目的
3. 対象利用者
4. 用語定義
5. 機能要件(利用者の行動単位でグループ化。IDはF-XX)
6. 認証(操作ごとの認証要否)
7. 非機能要件
8. 制約条件
9. スコープ管理(第1イテレーションの範囲/次期以降に持ち越すもの)
10. 進行管理(判断地点、完了の定義)
11. 開発運用方針

必要に応じて増減してよいが、増減した場合は章番号を振り直し、
本文中の相互参照(「6. 認証に従う」等)も合わせて修正する。

## 6. 機能要件のID・粒度

- IDは F-XX の連番。画面単位ではなく「利用者が達成したいこと」の単位で振る
- 1つのF-XXは1つの検証可能な振る舞いに対応する(テスト仕様書と1対1にできる粒度)
- 章(5.X)は「利用者の行動の種類」でグループ化する(例: 問題を作る/問題を共有する)

NG(1つのIDに複数の振る舞いが混在):
「F-09 アカウントを作成し、認証する」
→ 新規登録とログインで画面が分かれるなら、本来はF-09(登録)とF-10(認証)に
  分けたほうが詳細設計・テスト仕様との対応が取りやすい。
  ただし2ヶ月規模のプロジェクトでは、画面が分かれても要件として1つに
  まとめてよい場合もある。対応する詳細設計書が複数に分かれる時点で気づければよい

OK(1つの振る舞いに対応):
「F-03 問題に対する自分の回答を盤面上に示す」
→ 1つの操作、1つの画面、1つのテストに対応する

## 7. 修正時の必須チェック

要件定義書を修正するたびに、以下を確認する。

- [ ] 章番号・節番号が連番になっているか(削除・追加・移動のたびに崩れやすい)
- [ ] 本文中の章番号への参照(「6. 認証に従う」等)が実際の章番号と一致しているか
- [ ] 削除した項目への参照が他の要件・他の設計書に残っていないか
- [ ] 実現方法にあたる記述が紛れ込んでいないか(基本設計書に移せないか再確認する)
- [ ] 文末の句点、文体(常体)が統一されているか
- [ ] 括弧書きの補足が付いていないか

## 8. 基本設計書との役割分担

要件定義書を書きながら「これは実現方法では?」と迷ったら、機械的に
基本設計書側に書く。要件定義書は薄く保つことを優先する。

基本設計書に書くもの:
- 画面一覧・URL・画面遷移図
- 要件ごとの実現方式(表形式。「要件 → 実現方式」の対応)
- 共通コンポーネントの仕様
- 技術スタック、システム構成

## 9. 出力形式

- Markdownで作成する
- 表を積極的に使う。箇条書きの羅列より表のほうが一覧性が高い場合は表にする
- 図が必要な場合はMermaid記法を使う(画面遷移図、ER図等)
