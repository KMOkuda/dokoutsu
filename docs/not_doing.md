# やらないこと

> このプロジェクトで検討したが、採用しなかった構成、または
> 対応を先送りした機能をまとめる。

---

## 1. 採用しなかった構成

基本設計書「1.2 技術スタック」で決定した構成に対して、
検討した上で採用しなかった代替案とその理由を記録する。

| 構成 | 不採用の理由 |
|---|---|
| React / Next.js | 生成コードをレビューできないため |
| Supabase単体(サーバーレス) | サーバー側の処理を持てないため |
| Railwayダッシュボードでの起動コマンド直接設定 | コードとして残らず、他のサーバー環境に移行した際に同じ手順を再現できないため |
| 囲碁ライブラリ(WGo.js、Glift等) | 中身をレビューできないため。主要なものがCanvasベースであり、SVG採用の利点(交点ごとのイベント登録、CSSでのスタイル指定)が失われる。また棋譜再生を主用途としており、本アプリの用途(局面の組み立て、1手の着手)とは合わない |

---

## 2. 次期以降に持ち越す機能

第1イテレーションの範囲(要件定義書「8.1 第1イテレーションの範囲」)には
含めず、対応を先送りした機能。

| 内容 | 保留の理由 |
|---|---|
| 既存の詰碁の取り込み | データの調達・整備に時間を要するため |
| 自分の対局からの局面切り出し | 棋譜の読み込み機能が必要なため |
| 複数手の手順・変化の表示 | 実装量が大きいため |
| 棋譜解析・AIによる講評 | 実装規模が本プロジェクトの範囲を超えるため |
| グループ機能・友達機能 | 共有の仕組みとして必須ではないため |
| 本番環境のAWS移行(Docker) | Docker・AWSの学習と構築に時間を要するため。第1イテレーションはRailwayで完成させ、動作を確認してから移行する |
| 受付終了後の問題を回答非公開にする機能 | 締切後は公開方式によらず誰でも閲覧可能になる仕様(基本設計書「3.1 回答一覧の公開制御」)を踏まえ、受付終了の問題一覧から個別に非公開にできるようにしたい、という要望があった。URLはUUIDで推測不可能であり、扱うデータも機微情報ではないため、セキュリティ上必須とまでは言えないと判断し、今回は見送る。運用してみて必要性が高いと分かれば改めて検討する |
